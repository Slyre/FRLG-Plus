# Soul Link audit — 8 October 2026

Corrections delivered: see [AUDIT_FIXES_2026-10-08.md](AUDIT_FIXES_2026-10-08.md). The findings below preserve the original audit evidence.

## Outcome

Six confirmed defects: two P1 gameplay/recovery problems and four P2 correctness or usability problems. Existing tests pass but do not exercise these cases. No production code, player ZIP, ROM or personal save/settings file was changed by the audit.

P1 means a normal supported path can lose a Pokémon or stop automatic Internet recovery. P2 means a conditional gameplay blockage, startup failure from invalid optional data, or incorrect companion output. Priorities describe consequences, not measured frequency.

## Confirmed findings

### 1. P1 — A transport error can stop the companion and its reconnect loop

Location: [companion_core.py:455](</C:/Pokemon Soul Link/FRLG-Plus/remote/companion_core.py:455>), [companion_core.py:615](</C:/Pokemon Soul Link/FRLG-Plus/remote/companion_core.py:615>), [network.py:618](</C:/Pokemon Soul Link/FRLG-Plus/remote/network.py:618>).

When replaying a pending death, `coordinate()` awaits `wan_send()` without containing a transport exception. If the socket has dropped while `joined` still says true, `ConnectionResetError` escapes `DesktopBridge.run()`. `network.run()` observes that task finishing and cancels every other task, including `connect_forever()`. A recovery proposal uses another automatic send path exposed to the same class of failure.

Consequence: a brief Internet interruption can require manually restarting the launcher instead of reconnecting automatically. This audit does not demonstrate lost durable death records; the confirmed defect is loss of continued service/recovery.

Evidence: a real TCP loopback connection reset with `SO_LINGER=0` and `transport.abort()` caused `DesktopBridge.run()` to exit with `ConnectionResetError: Connection lost` when sending a pending death. The receiving loop was intentionally absent to isolate the legitimate ordering where a send detects failure before `joined` is cleared. An injected-error probe separately confirmed propagation. This was not a live VPS or two-PC test.

Repair target: contain expected transport errors at the coordinator/connection boundary, mark the connection unavailable, preserve journals and keep reconnect supervision alive. Add a test where automatic death replay and disconnect overlap, followed by successful reconnection.

### 2. P1 — Receiving an egg consumes the encounter twice and kills it on hatch

Location: [soul_link_local.c:237](</C:/Pokemon Soul Link/FRLG-Plus/src/soul_link_local.c:237>), [daycare.c:1892](</C:/Pokemon Soul Link/FRLG-Plus/src/daycare.c:1892>).

With Nuzlocke and Soul Link enabled, successful egg acquisition records the encounter and consumes its area. The old hatch routine checks that same area's Nuzlocke flag again and sets the hatched Pokémon's HP to zero. Field processing then records a permanent death, which can propagate to the partner.

Evidence: a native mGBA fixture called the actual ROM routines with a new area and a non-duplicate egg. `GiveMonToPlayer()` succeeded with HP 19 and consumed-area flag 1; `AddHatchedMonToParty()` produced HP 0; `SoulLink_ProcessField()` recorded `ENCOUNTER_DEAD`. The fixture uses an artificial Route 2 state to isolate these functions; daycare egg receipt uses the same acquisition path. A full ordinary playthrough to the daycare was not performed.

Repair target: use one encounter ownership rule for egg receipt and hatch. A legal recorded egg must not be counted as a second acquisition. Retain standalone Nuzlocke behavior when Soul Link is disabled and test both gift and daycare eggs.

### 3. P2 — Generated Shedinja conflicts with Ninjask's pair identity

Location: [evolution_scene.c:558](</C:/Pokemon Soul Link/FRLG-Plus/src/evolution_scene.c:558>), [soul_link_team.c:15](</C:/Pokemon Soul Link/FRLG-Plus/src/soul_link_team.c:15>), [soul_link_team.c:95](</C:/Pokemon Soul Link/FRLG-Plus/src/soul_link_team.c:95>), [soul_link.c:541](</C:/Pokemon Soul Link/FRLG-Plus/src/soul_link.c:541>).

The generated Shedinja copies Ninjask's OT/personality. Team preparation counts both as matching the Ninjask pair and refuses the selection as `SOUL_LINK_TEAM_DUPLICATE`, including when Shedinja is in the PC. Pair lookup separately excludes Shedinja, so it is not governed by the paired death record. With Soul Link enabled and standalone Nuzlocke disabled, fainting and healing it restores its HP.

Evidence: actual `CreateShedinja()` in the native fixture produced the copied identity. Ninjask selection was refused with reason 4, then the identical selection passed after removing only Shedinja from the fixture. Shedinja KO, death recording and healing produced HP 1 and `IsBoxMonDead=false` in the Soul Link-only configuration.

Repair target: explicitly define the extra evolution Pokémon's pair/encounter policy and apply it consistently to identity matching, party locks and permanent deaths. Do not solve this by allowing genuine duplicate identities to bypass validation.

### 4. P2 — Invalid optional history data prevents the network from starting

Location: [companion_core.py:207](</C:/Pokemon Soul Link/FRLG-Plus/remote/companion_core.py:207>).

`ActivityLog` calls `data.get()` without first confirming that decoded JSON is an object. The loader does not catch `AttributeError`. Because this optional log is constructed during `DesktopBridge` initialization, valid JSON of the wrong shape prevents the entire network companion from starting.

Evidence: isolated `duo-history.json` files containing `[]`, `null` and `42` each caused `AttributeError`. Real player files were not changed. This requires invalid historical data; the audit does not claim ordinary atomic writes generate those values.

Repair target: validate the top-level schema before accessing properties and ignore or quarantine invalid optional history. Test malformed syntax and valid JSON of incorrect types.

### 5. P2 — Delayed readings generate false reverse evolutions

Location: [companion_core.py:237](</C:/Pokemon Soul Link/FRLG-Plus/remote/companion_core.py:237>), observation call sites at lines 321 and 388.

Local and peer readings feed the same encounter history. Every species difference is interpreted as an evolution without checking the source's authority or freshness for that Pokémon. An evolved peer reading followed by an older local reading generates a reverse evolution and increases the session counter twice.

Evidence: the actual `DesktopBridge.snapshot/message` paths were exercised with Rattata, then Raticate from the peer, then an older Rattata reading. The journal recorded `19 → 20` and `20 → 19`, and the session evolution counter became 2. A separate direct `ActivityLog.observe()` probe reproduced this output.

Consequence: inaccurate journal/session data. This finding does not imply that the ROM or the Pokémon is reverted.

Repair target: record each player's species evolution from an authoritative current reading or use a monotonic versioned update. Do not infer a reverse evolution merely from differing snapshots.

### 6. P2 — Location search omits supported areas 39–86

Location: [app.js:1](</C:/Pokemon Soul Link/FRLG-Plus/remote/companion-web/app.js:1>), [app.js:145](</C:/Pokemon Soul Link/FRLG-Plus/remote/companion-web/app.js:145>), [nuzlocke_areas.h:41](</C:/Pokemon Soul Link/FRLG-Plus/src/data/nuzlocke_areas.h:41>).

`areaName()` supplies names only for areas 1–38 and Starter. Other supported areas appear as `Area N`, and `findPairs()` searches only that incomplete label.

Evidence: searches for Safari (39), Rock Tunnel (40) and Power Plant (44) returned zero matches for pairs in those areas; searching `Area 40` found the Rock Tunnel pair. Native area definitions include these places and the island areas.

Repair target: expose the full canonical area mapping to the companion and derive labels/search from one source. Include representative mainland and island areas in tests.

## Limits and excluded candidates

No separate-PC Internet session, live VPS deployment or clean Windows-account installation was performed. The relay/TLS configuration and the local web token/Origin protections were inspected; no additional defect was confirmed there. No notification permission was requested and no live player game was used.

Reuse of the same room code after a new game was not reported as a defect: the existing guide explicitly requires two fresh saves and a new code. Gift-script and NPC-trade candidates did not yield a confirmed defect and are excluded.

There is no evidence here of an additional dramatic ping reduction to pursue. Correct recovery and gameplay rules take priority over more features or transport changes. After corrections, qualification still needs two actual PCs on different Internet connections, including a brief outage while deaths and approved team changes are pending.

Recommended order: transport exception containment; egg receipt/hatch ownership; Ninjask/Shedinja policy; optional-history validation; authoritative evolution events; complete location mapping.
